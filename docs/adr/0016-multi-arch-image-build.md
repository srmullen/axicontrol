# Multi-arch (amd64+arm64) image build, QEMU-emulated, arm64 verified only at release

[ADR-0001](./0001-node-pinned-device-access.md) pins the pod to the one k8s node the AxiDraw is physically wired to. That node is a 64-bit Raspberry Pi (`linux/arm64`). The image built by [ADR-0013](./0013-build-ci-and-publish.md)'s Dagger pipeline was only ever built for `linux/amd64` — Dagger's `Directory.DockerBuild()` with no `Platform` option defaults to the Dagger engine host's platform, which is `amd64` on the GitHub Actions runner. Deploying that image to the Pi node fails immediately with `exec /axicontrold: exec format error`: the container runtime can't execute an amd64 ELF binary under an arm64 kernel.

The fix is to publish a multi-arch image — `linux/amd64` and `linux/arm64` under one tag — so the tag the homelab repo already references works on the Pi node without that repo needing to know or care about architecture. `ci/main.go`'s `Build` now takes an explicit `Platform` parameter instead of relying on Dagger's implicit host-default; `Publish` builds every platform in a `buildPlatforms` list and merges them into one manifest via `Container.Publish`'s `PlatformVariants` option, publishing from a fresh `dag.Container()` carrying the GHCR registry auth rather than from one of the platform-specific build outputs.

Cross-platform builds run under QEMU emulation of the *entire* build (Go compile, `apt-get`, `pip install`), not by cross-compiling just the Go binary via `--platform=$BUILDPLATFORM` + `TARGETARCH`. This means the Dockerfile needed no changes at all: `go build` has no `GOARCH` override, so it simply compiles for whatever architecture the emulated container reports natively. The tradeoff is slower arm64 builds (QEMU emulates `apt-get`/`pip install` too, not just the compile step) — acceptable because arm64 only builds inside `Publish`, which only runs on a deliberate GitHub Release ([ADR-0015](./0015-split-ci-release-workflows.md)), not on every push. `ci.yml` (push-to-main) keeps verifying only `linux/amd64` (pinned explicitly as `ciPlatform`, same reasoning as pinning `Build`'s platform generally) so routine pushes stay fast and emulation-free; an arm64-specific build break would surface at release time, when `Publish` re-runs the full `CI` gate anyway.

GitHub's standard `ubuntu-latest` runner has no arm64 binfmt handler registered by default, so `release.yml` gained a `docker/setup-qemu-action` step (registering `arm64` emulation) before the Dagger action runs — a host-level prerequisite for Dagger's buildkit-based engine to execute foreign-arch binaries under emulation at all, regardless of which cross-platform strategy was chosen.

## Considered Options

- arm64-only image (drop amd64 entirely) — rejected: loses the ability to `docker run` the image locally on an amd64 dev machine for testing without cross-arch overhead; multi-arch costs nothing extra for consumers pulling by tag, since `docker pull` already selects the right platform automatically.
- Cross-compile the Go binary via `FROM --platform=$BUILDPLATFORM ... AS builder` + `ARG TARGETARCH` + `GOARCH=$TARGETARCH`, emulating only the final Python stage — rejected: saves build time on the (fast, cgo-free) Go compile step specifically, at the cost of a less obvious Dockerfile, for a build that already only runs at release time and isn't a hot path worth optimizing yet.
- Native `arm64`-hosted GitHub Actions runners (`ubuntu-24.04-arm`), avoiding emulation entirely — rejected: requires restructuring `release.yml` into a multi-job matrix and merging platform images into one manifest across jobs (e.g. via `docker buildx imagetools create`), adding real workflow complexity and moving pipeline logic out of the portable Dagger module and back into GitHub Actions YAML, contrary to ADR-0013's "thin trigger" principle.
- Building and verifying `linux/arm64` in `ci.yml` on every push to `main`, not just in `Publish` — rejected: pays QEMU emulation cost on every push for a failure mode (arch-specific build breaks) that's rare for this codebase's dependency set; `release.yml` already re-runs the full `CI` gate before publishing, so a broken arm64 build still can't reach GHCR, it's just caught later, at the deliberate release step rather than on every commit.
