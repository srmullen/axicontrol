# SVG upload sanitization plus &lt;img&gt;-tag preview rendering, together

Uploaded SVGs are served directly by the single backend ([ADR-0007](./0007-single-backend-service.md)) so the browser can render "the file that will be plotted," but SVG can embed `<script>` tags and event-handler attributes, making direct rendering of user-uploaded content an XSS surface. We use both defenses rather than either alone.

**Sanitize at upload time**: the sanitization pass that already strips AxiDraw-specific per-layer option overrides ([ADR-0003](./0003-device-config-and-presets.md)) is extended to also strip `<script>` tags, event-handler attributes, `javascript:` URIs, and `foreignObject`-embedded HTML. This costs nothing functionally — `axicli` only reads path/shape data, so scripts have zero effect on plot output.

**Serve the preview via `<img>`**: not inline embedding, `<object>`, or `<iframe>`. SVGs loaded via `<img>` run in browsers' strictest built-in security context — script tags and event-handler attributes never execute there — which satisfies the "restricted rendering context" half without building or maintaining a custom CSP/sandboxing scheme.

**Why both**: `<img>`'s script-blocking is context-specific — it only applies when the file is rendered through that tag. The same file opened directly (a raw download link, "open in new tab") still executes embedded scripts under axicontrol's own origin, and since uploads are retained indefinitely as a design library ([ADR-0005](./0005-filestore-abstraction-over-persistent-volume.md)), future direct-access paths are plausible. Sanitization travels with the file to any such consumer; `<img>` is the cheap defense for the preview path specifically that doesn't depend on the sanitizer having zero bypasses. Checkpoint SVGs ([ADR-0008](./0008-checkpoint-file-persistence.md)) inherit this for free, since `axicli` only adds resume-position metadata to an already-sanitized input and never reintroduces script content.
